# Head Loss: instructions for Claude Code

Head Loss (working title) is a relaxing, minimal, top-down 2D idle/incremental game for PC (Steam), built in Unity 6.x (6.6 or newer). The player designs real pipe and duct networks inside procedurally generated buildings across a procedurally generated city. Outlets that receive enough flow earn money. The physics is real engineering math, shown to the player as heatmaps.

This file holds the rules and the workflow. The full design lives in `docs/spec/`. **The spec is the source of truth. Build exactly what it says, down to the small details.** Read `docs/spec/00-index.md` first in every new session, then the spec files for the phase you are working on.

---

## 1. Hard rules

1. **Phase by phase, with gates.** Build only the current phase from `docs/spec/14-roadmap.md`. When its tasks are done and tests pass, write the phase report, then **stop and wait for the user to playtest and approve the gate**. Never start the next phase without an explicit "gate passed" from the user.
2. **Do not invent design.** If the spec does not cover something you need, pick the simplest option consistent with the spec, log it in `docs/dev/decisions.md` with a `NEEDS CONFIRMATION` tag, and mention it in your next message. If the choice is big (changes gameplay, economy or scope), ask before building it.
3. **Do not drop design.** Everything in the spec must end up in the game in its assigned phase. If something turns out to be impossible or badly unfun, say so and propose an alternative; do not silently skip it.
4. **Simulation is pure C#.** No `UnityEngine` references in `HeadLoss.Core`, `HeadLoss.Sim` or `HeadLoss.Game` (enforced with `noEngineReferences: true` in their `.asmdef`). Unity code is a thin view/input/rendering layer on top. See `docs/spec/01-architecture.md`.
5. **SI units inside the simulation, always.** Pa, m³/s, kg/s, K or °C (documented per field), m, W, J, s. Convert to display units (m³/h, bar, mbar, °C, kW) only in the UI layer, through `HeadLoss.Core.Units`.
6. **Every tunable number lives in data files**, never hard-coded: `Assets/HeadLoss/Data/*.json`. Defaults are in `docs/spec/13-balancing.md`. Physical constants and fluid property tables are data too.
7. **Tests first for physics and rules.** Every formula in `docs/spec/05-simulation.md` gets an EditMode test, including the reference cases in `docs/spec/15-testing.md`. A phase is not done while any test fails.
8. **No external assets.** All visuals and audio are generated by code (meshes, shaders, procedural textures, synthesized sound). No Asset Store packages, no downloaded art, no fonts beyond Unity's default and Google Fonts with OFL licences committed to the repo.
9. **Allowed packages only:** see `docs/spec/01-architecture.md` §Packages. Ask before adding any other.
10. **Determinism.** All generation and all random gameplay rolls use the seeded RNG in `HeadLoss.Core.Rng` (PCG32). Never `UnityEngine.Random` or `System.Random` in game logic. Same seed must give the same city, the same buildings and the same failure rolls.
11. **Fast Enter Play Mode is on by default in Unity 6.6 (no domain reload).** Never keep mutable `static` state in Unity-side code. If you must, reset it in a `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` method.
12. **Calm by default.** No flashing, no screen shake, no loud sounds, no punishing pop-ups. Warnings are quiet icons with a short reason. This applies to every phase.
13. **Mobile-ready UI.** Every hover interaction must also work by tap/select. Minimum hit target 44 × 44 px at 1080p reference. Use UI Toolkit with a scalable panel.

## 2. Working with the Unity Editor (Unity CLI)

The user keeps the Unity Editor open with the official Unity CLI enabled. The Unity CLI (`unity` command, beta) talks to the running Editor through the `com.unity.pipeline` package. Its command set changes between releases, so **do not assume command names**:

1. At the start of each session run `unity --version`, `unity --help` and `unity command --help` (or the equivalents the help output points to). Record what works in `docs/dev/unity-cli-notes.md` and reuse it.
2. If `unity` is not on PATH, check the install location from the help/docs, then ask the user. Never install anything yourself without asking.
3. Use the CLI to: refresh assets / trigger compilation, read the console for errors, run EditMode and PlayMode tests, enter/exit play mode, take screenshots, and make builds.
4. After every code change: trigger a refresh, wait for compilation, read the console. Fix all compile errors and warnings you introduced before moving on.
5. If the CLI cannot do something (for example run tests while the Editor is busy), say exactly what you need the user to click, and continue with other work.
6. Do not run Unity in `-batchmode` against the project while the Editor has it open (the project is locked). Batchmode is only for CI or when the user closes the Editor.

## 3. Session workflow

1. Read `docs/spec/00-index.md`, `docs/dev/progress.md`, `docs/dev/decisions.md` and the spec files for the current phase.
2. Check `git status`. Work on a branch named `phase-N/<short-task>`; merge to `main` when the task is done and tests pass.
3. Pick the next unchecked task in `docs/dev/progress.md` (create it from the phase task list in `14-roadmap.md` on first run).
4. For simulation and rules: write the tests, then the code, then run the tests.
5. For Unity-side work: build it, enter play mode through the CLI, take a screenshot, look at it, fix what looks wrong.
6. Commit with a message like `phase-2: payout bands and code-max zero payout`.
7. Tick the task in `progress.md`. Keep going until the phase is done.
8. At phase end: run all tests, make a Windows standalone build into `Builds/phase-N/`, write `docs/dev/phase-N-report.md` (what was built, how to playtest, gate checklist from `14-roadmap.md`, known issues, decisions needing confirmation), then **stop and ask the user to playtest the gate.**

First session only: create the Unity project structure, assembly definitions, packages and folders from `01-architecture.md`, `.gitignore` for Unity, `git init`, and the `docs/dev/` files (`progress.md`, `decisions.md`, `unity-cli-notes.md`).

## 4. Code conventions

- C# with the Unity 6 default language version. Nullable reference types enabled in pure assemblies (`#nullable enable` or csc.rsp).
- Namespaces match folders: `HeadLoss.Sim.Network`, `HeadLoss.Game.Economy`, and so on.
- Plain data classes for state (serializable to JSON), separate stateless systems that operate on them. No singletons in sim code; pass a `GameContext`.
- `double` in the network solver and economy; `float` is fine in the room grid and rendering.
- Public API documented with `///` summaries that state units, e.g. `/// <param name="flow">Volumetric flow, m³/s.</param>`.
- No LINQ in per-tick hot paths. No allocations in per-frame Unity code (use pooled buffers).
- Names from the spec glossary (`00-index.md`) are used exactly, in code and UI.
